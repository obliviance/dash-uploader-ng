Drop-in audit

Every line of the eight shared Python modules, four JS files and three stylesheets, compared against pristine upstream. Eleven behaviours differed. Nine are resolved in 1.3.0; the other two are kept, for a reason.

Three modules are byte-identical once the package rename is undone. Every public signature only gained keyword arguments with defaults, appended last. No component prop was removed. No CSS rule was dropped. Files land in exactly the same places.

Each finding below carries what was done about it. The two marked kept are the ones where matching upstream would have meant reintroducing a defect that damages the host application.

Tier 1 — refused to installEnvironment floors were raised

Neither is a code defect, but both stop the swap before it starts and neither is announced in the migration note, which says only that the import name changed.

F-01Resolved in 1.3.0 Python floor raised to 3.10 from “unspecified”
upstream setup.py
(no python_requires at all)
utils.py still branches on
  sys.version_info < (3, 8)
fork pyproject.toml
requires-python = ">=3.10"

Upstream shipped no python_requires, and its own utils.py carries a pkg_resources fallback for Python < 3.8 — so it was installable and functional well below 3.10. That fallback is still present in the fork as dead code.

Breaks any app on Python 3.7–3.9. pip install fails outright with no available version.

Done requires-python = ">=3.8". The only blocker was Path.is_relative_to (3.9+), now Path.relative_to in a try/except ValueError — identical semantics here. CI matrix extended to 3.8 and 3.9.

Tier 2 — accepted upstream, refused hereInput validation had narrowed

The CVE-2026-38360 fix validates every client-supplied path component at the request boundary. It is correct to do so — but the accepted character set is narrower than the traffic real apps generate, and the rejections surface to the end user as “Unexpected error while uploading … Please reupload the file.”

F-03Resolved in 1.3.0 upload_id charset is narrower than the values apps actually pass

This is the highest-impact finding. upload_id is an explicit public parameter of du.Upload(), and the documented pattern is to derive it per user or per session. safe_segment requires ^[A-Za-z0-9][A-Za-z0-9._-]*$ — which excludes e-mail addresses, ISO timestamps, and any identifier beginning with an underscore.

"user@example.com"200400session e-mail — high

"_private"200400leading underscore — medium
"user+tag"200400medium
"my session" · "sess:42" · "café" · "session."200400already pinned in tests

Note tests/test_upstream_parity.py::TestKnownIntentionalNarrowing pins only the last four. The e-mail, ISO-timestamp and leading-underscore cases are unrecorded — they read as oversights rather than decisions.

Fix Widen to allow @ + : ~ and a leading underscore — none of which are path separators or traversal primitives — while keeping the ensure_within backstop. Or percent-encode the segment rather than rejecting it.

Done safe_segment now refuses only what cannot be one path component: empty, a separator, ./.., a null or control character, over-length. Every value in the table above is accepted again. ensure_within was and remains the boundary that holds — the CVE proof of concept is still blocked, with nothing written outside the root.

F-04Resolved in 1.3.0 Filenames legal on Linux and macOS are refused

Filename handling is otherwise generous — spaces, parentheses, commas, &, %, #, apostrophes, brackets and full Unicode all survive intact, which is better than secure_filename would have managed. Four classes do not.

uploaded filenameupstreamforkreason given
"données.csv" · "報告書.xlsx" · "отчет.csv"200200—
"my report (final).xlsx" · "data,2024.csv" · "100%.csv"200200—
".env" · ".gitignore"200400resolves to a dotfile
"nul.txt" · "con.log" · "aux.csv" · "prn.pdf"200400reserved device name on Windows
"com1.dat" · "lpt1.txt"200400reserved device name on Windows

The Windows-reserved and trailing-dot rules are applied on every platform by design, so that a file accepted on a Linux host can later be served from a Windows one. That is defensible; it is just not what upstream did, and aux.csv is an ordinary spreadsheet name.

Note Unlike upload_id, there is no parity test recording these as intentional divergences — only safepath unit tests asserting the rejection.

Done Dotfiles, Windows device names and trailing dots or spaces are accepted again. safepath.STRICT_SEGMENTS = True restores the strict rules for deployments that need Windows portability or do server-side extension checks.

F-05Resolved in 1.3.0 Uploads above 100,000 chunks are refused
upstream
flowTotalChunks: unbounded
250000 chunks → 200 OK
fork
MAX_CHUNKS = 100_000
250000 chunks → 400

A DoS guard, since the completeness check materialises one path per chunk. At the 1 MB default that still permits ~100 GB. It becomes reachable if an operator raises max_file_size past 100 GB, or lowers chunk_size below the default on a large file.

Breaks very large uploads, silently, with a generic “Invalid upload request”. Worth raising the ceiling or scaling it with chunk size.

Done MAX_CHUNKS raised 100× to 10,000,000 — about 10 TB at the default chunk size — and reassembly now builds its chunk paths lazily, so nothing is materialised per chunk.

Tier 3 — same status codes, different behaviourSemantics that had shifted underfoot

F-06Resolved in 1.3.0 post_after() and get_after() no longer run when a request fails
upstream — measured
_post() raises
status = 500
hooks  = [before, _post, after]
fork — measured
_post() raises
status = 500
hooks  = [before, _post]

Upstream swallowed the exception and returned None, so the post_after() line in the documented subclass template still executed before Flask turned the None into a 500. The fork calls abort(500), which raises past it.

This is the extension point upstream's own security guidance points at, and the change is recorded only in a code comment. The complementary case is better: an abort(403) from post_before() — the documented auth pattern — still returns 403 on both.

Breaks custom HttpRequestHandler subclasses using post_after for cleanup, audit logging, metrics or lock release. Failures now skip it with no warning.

Done post_after and get_after now run from a finally, so they fire on both the success and the failure path, as they did upstream.

F-07Resolved in 1.3.0 settings.UPLOAD_FOLDER_ROOT became a read-only mirror
upstream
settings.UPLOAD_FOLDER_ROOT = "/new"
callback reports:
  /new/sess1/r.csv
fork — measured
settings.UPLOAD_FOLDER_ROOT = "/new"
callback reports:
  /tmp/orig/sess1/r.csv   (unchanged)

Reading the global still works and still reflects the default configuration. Writing it no longer reaches du.callback, which now resolves the folder from the registered UploadConfig. This was the only workaround for upstream #17 (“change the destination folder dynamically”).

Breaks apps mutating the global. The equivalent that works: settings.get_config(id).upload_folder_root = "/new" — worth documenting, since the old form now fails silently rather than loudly.

Done settings.upload_folder_root_for() prefers the module global for components on the default configuration, and the registered config only for components with a named one. Assigning to the global works again; multi-uploader routing is unaffected.

F-08Resolved in 1.3.0 Flask endpoint names changed
upstream — measured
['get', 'post']
fork — measured
['dash_uploader_ng_API_dash_uploader_get',
 'dash_uploader_ng_API_dash_uploader_post']

Deriving the endpoint from the API path is what makes a second configure_upload() possible at all, and the old names were generic enough to collide with an app's own routes. But anything addressing them by name breaks.

Breaks app.view_functions["post"], url_for("post"), and CSRF exemptions written against the old names — the exact pattern docs/deployment.md now documents differently.

Done The first uploader on a server registers under get / post again. Only a second configure_upload() falls back to path-derived names, since those are taken by then — so every app that could have worked upstream keeps the old names.

F-09Resolved in 1.3.0 One extra GET per chunk, on by default

testChunks moved from a hard-coded false to this.props.resumable, default true. A 1 GB upload at the default chunk size now issues ~1,024 additional GET requests to the upload endpoint.

Affects apps behind a WAF, rate limiter, or reverse proxy whose rules only anticipated POST to that path. du.Upload(resumable=False) restores upstream's traffic exactly.

Done resumable defaults to False, matching upstream's hard-coded testChunks: false. Swapping the import now changes nothing about what reaches your server. Opt in with du.Upload(resumable=True).

F-10Kept deliberately Bundled Bootstrap fragments no longer leak into the host page

All 241 rules in button.css are preserved verbatim and every one is now scoped beneath .dash-uploader-root — verified rule-for-rule, with no declaration block altered and nothing dropped. Inside the component, rendering is unchanged.

Outside it, an app whose own .btn, .progress or bare <progress> elements were being styled — knowingly or not — by dash-uploader's injected Bootstrap 4 fragments will now render unstyled. That is the point of the fix (upstream #91, #43), but it is a visible change on upgrade.

Affects apps that inherited the leak. Restoring it means importing Bootstrap properly.

Kept Not reverted. Every other item restores behaviour an app might depend on; this one's \u201cbehaviour\u201d is damage to code that has nothing to do with the component. Reverting would deliberately reintroduce upstream #91 and #43. All 241 rules render identically inside the component — only the leak is gone.

MethodHow this was established

Pristine upstream was cloned at e1a1af4 — the last commit before the repository was archived on 2025-07-19 — and every shared file diffed after normalising dash_uploader_ng back to dash_uploader.

Behavioural claims come from running both handlers side by side in Flask test clients over the same request corpus: 18 upload_id values, 28 filenames, both use_upload_id modes, four chunk counts, a failing _post, and an abort() from post_before. Every “measured” figure on this page is an observed status code or hook trace, not a reading of the source.

CSS was compared rule-by-rule rather than line-by-line: comments stripped, selector lists split, declarations sorted, the .dash-uploader-root prefix removed, then the two rule sets diffed as multisets. button.css loses 45 lines to selector-list collapsing and no rules.

Not covered: behaviour on Windows and macOS hosts, and Dash versions other than the 4.x used here.
